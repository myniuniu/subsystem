## 简介
本贡献指南旨在为开发者提供清晰的代码提交流程、质量审查标准和开发实践。项目基于React技术栈，采用现代化前端开发工具链，遵循严格的代码质量和格式化标准。通过本指南，新贡献者可以快速了解项目规范并融入开发团队。

## 代码规范

### JavaScript/JSX编码规范
项目使用ESLint进行代码检查，确保代码质量和一致性。根据`package.json`中的lint脚本配置，所有JavaScript和JSX文件都需要通过ESLint检查。

```json
"scripts": {
  "lint": "eslint . --ext js,jsx --report-unused-disable-directives --max-warnings 0"
}
```

**缩进规则**：使用2个空格进行缩进，不使用Tab字符。

**命名约定**：
- 组件命名采用PascalCase（大驼峰式）
- 文件命名采用kebab-case（短横线分隔）
- 变量和函数命名采用camelCase（小驼峰式）

**语句结束**：所有语句必须以分号结尾，确保代码解析的确定性。

**组件设计模式**：
- 采用函数式组件 + Hooks模式
- 状态管理使用useState和useEffect
- 组件间通信通过props传递
- 样式采用CSS Modules

**代码组织**：
- 按功能模块组织代码
- 公共组件和工具函数分离
- 样式文件与组件文件对应

## 测试与构建

### 测试套件运行
项目目前未在`package.json`中定义明确的测试脚本，但根据《需求文档.md》中的测试要求，项目应具备以下测试能力：

- **单元测试**：覆盖组件功能和工具函数，测试覆盖率需大于80%
- **集成测试**：验证模块间交互和API接口
- **端到端测试**：确保完整用户流程的正确性
- **性能测试**：监控页面加载性能和内存使用情况

### 构建工具配置
项目使用Vite作为构建工具，配置文件`vite.config.js`定义了开发服务器和构建输出的相关设置。

```javascript
export default defineConfig({
  plugins: [react()],
  server: {
    port: 3000,
    open: true,
    hmr: {
      overlay: true
    }
  },
  build: {
    outDir: 'dist',
    sourcemap: true
  }
})
```

**构建命令**：
- `npm run dev`：启动开发服务器，监听3000端口
- `npm run build`：生产环境构建，输出到dist目录
- `npm run preview`：预览生产构建结果

**构建特性**：
- 支持热模块替换（HMR）
- 自动生成source map便于调试
- 开发时自动打开浏览器

## 版本控制

### Git提交消息格式
为了保持提交历史的清晰和可追溯性，项目采用标准化的提交消息格式：

**提交消息结构**：
```
<类型>: <简短描述>

<详细描述>

<关联信息>
```

**类型说明**：
- feat：新增功能
- fix：bug修复
- docs：文档更新
- style：代码格式调整（不影响逻辑）
- refactor：代码重构
- test：测试相关更改
- chore：构建过程或辅助工具变动

### 分支管理策略
项目采用基于功能的分支管理策略：

**主分支**：
- `main`：主分支，保护分支，仅通过Pull Request合并

**开发分支**：
- `develop`：集成分支，用于日常开发集成

**功能分支**：
- `feature/<功能名称>`：功能开发分支
- `bugfix/<问题描述>`：bug修复分支
- `hotfix/<紧急问题>`：紧急修复分支

**Pull Request审查流程**：
1. 创建Pull Request，关联相关issue
2. 至少一名核心成员进行代码审查
3. 通过CI/CD流水线检查（包括ESLint检查）
4. 解决所有审查意见后合并
5. 合并后自动更新变更日志

## 调试技巧

### 开发服务器调试
利用Vite提供的开发服务器特性进行高效调试：

**热重载**：修改代码后浏览器自动刷新，支持状态保留。

**错误覆盖层**：开发服务器配置了`hmr.overlay: true`，可在浏览器中直接显示编译错误和警告。

**源码映射**：构建时生成source map，便于在浏览器开发者工具中调试原始源码。

### 组件调试
对于复杂的React组件，如`UnifiedAICenter.jsx`中的智能提示功能，可以使用以下调试方法：

```jsx
// 在智能提示组件中添加调试信息
const SmartSuggestions = () => {
  console.log('渲染智能提示', suggestions);
  return (
    // 提示内容
  );
};
```

### API调用调试
对于服务调用，如`scenarioService.js`中的场景发布功能，可以通过拦截请求进行调试：

```javascript
// 在服务调用前后添加日志
const publishScenario = async (id, publishData) => {
  console.log('发布场景请求', { id, publishData });
  const result = await api.post('/scenarios/publish', { id, publishData });
  console.log('发布场景响应', result);
  return result;
};
```

### 状态管理调试
利用React DevTools监控组件状态变化，特别是复杂的状态逻辑，如场景审核状态转换：

```javascript
// 审核状态转换

  // 状态转换逻辑
  console.debug('审核操作', { scenarioId, approved, comments });
};
```

## 文档维护

### 文档更新义务
所有代码贡献者都有责任维护相关文档的同步更新：

**必须更新的文档**：
- 功能变更时更新`需求文档.md`
- 新增API时更新接口文档
- 修改配置时更新`README.md`
- 重要变更时更新`CHANGELOG.md`

### 变更日志维护
`CHANGELOG.md`是项目的重要历史记录，每次提交都应考虑是否需要更新变更日志。

**变更日志条目格式**：
```
## [版本号] - YYYY-MM-DD

### 新增功能
- 描述新增的功能

### 问题修复
- 描述修复的问题

### 改进优化
- 描述性能或体验改进
```

**自动化建议**：
考虑引入工具如`standard-version`或`conventional-changelog`来自动化变更日志的生成，基于Git提交消息自动生成变更条目。

**最佳实践**：
- 每个Pull Request都应包含变更日志更新
- 使用一致的术语描述变更类型
- 提供足够的上下文信息
- 避免过于技术性的描述，考虑读者理解
